| D26 | 2026-07-18 | Billing is **two-layer**. Layer 1 (internal, never exposed): every run/script/asset job links to `usage_events` covering **all** resource kinds — Apify results, Claude tokens, future Gemini/other model tokens, storage, compute allocation — each with quantity × unit_cost_usd, giving true cost per operation. Layer 2 (user-facing): credits («токены», 1 токен = $0.01 of user value); an operation burns `ceil(internal_cost_usd × X ÷ 0.01)` tokens, where **X is a tier-dependent markup factor** (initial config: $5 plan = 500 tokens, X=10; $20 plan, X=7; $100 plan, X=5 — adjustable). Users see **only tokens** — balance, and an itemized per-run/per-script token consumption history; X, internal USD costs, and unit prices never appear in any API response or UI | User requirement: transparent per-run token accounting for the customer, full multi-resource cost traceability for us, margin structure (X per tier) strictly internal. Example: a 20-competitor run costing us $0.10 burns 100 tokens for a $5-tier user (= $1 of value) |

| D32 | 2026-07-25 (revised same-day) | **E17 (Run Deep Analysis) comment scraping is dual-vendor**: **Apify's `apidojo/instagram-comments-scraper-api`** primary ($0.0075/post query, includes first 15 comments, +$0.0005/additional comment — ≈$0.0125/post at D34's 25-comment cap; reuses the `apify-client` dependency already pinned since E1-S1, no new integration surface for the primary leg), **Bright Data Instagram Scraper API** ($0.75/1,000 successful requests, pay-per-success) as automatic fallback when the primary actor fails a given post. Comment scraping is E17's dominant internal cost line (~95% of it, see D35) and Instagram gates comment visibility more aggressively than posts, so a blocked/failed vendor is more likely here than on the base pipeline. **Revised same-day** after evaluating `apidojo/instagram-comments-scraper-api` directly (100% reported run-success, ~1.2–1.4K users, 4.7–5.0 rating): it's cheaper than Bright Data at our cap (~$0.625 vs ~$0.9375 for a 50-post run) and needs zero new dependency since it's just another Apify actor called through the already-integrated `apify-client`. Originally the plan paired this actor as Bright Data's *fallback* behind the official `apify/instagram-comment-scraper`, but that pairs two Apify-hosted actors together — a platform-wide Apify outage would take out both, defeating the redundancy goal. Flipping the pairing (cheapest actor primary, cross-company Bright Data as the true backstop) is strictly better: cheaper, less code, and the redundancy claim actually holds. Bright Data's Instagram Scraper API remains confirmed to be the same "managed, no parser maintenance" shape as Apify's actors (send a URL, get structured JSON) — not a DIY proxy pool — so this doesn't reopen D2's rejection of self-built scraping |
